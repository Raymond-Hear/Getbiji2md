# 项目整理

## 这份文档是干嘛的

这份文档用来把分散在聊天、进度说明和零散笔记里的项目共识整理成一页。
如果之后隔一段时间再回来做这个项目，先看这里就能快速找回上下文。

## 项目现状

- 项目名：`Get2MD`
- 核心目标：把 Get 笔记导出成 Markdown
- 产品形态：公开落地页 + 独立工具页
- 当前阶段：轻量 MVP
- 当前定位：不是 SaaS

## 已经明确的核心方向

- 产品在文案和行为上都要坚持 local-first。
- 除非后面明确需要，否则不加登录、数据库、云同步。
- `API Key` 和 `Client ID` 一律视为敏感信息。
- 优先做简单静态前端，不轻易引入更重的技术结构。
- “介绍产品”和“实际操作工具”要分开：
  - `index.html` 负责落地页
  - `app.html` 负责工具工作台

## 已经聊清楚的事情

### 产品方向

- MVP 先聚焦一条清晰主路径：同步、筛选、预览、导出。
- 这个工具服务的是“想把自己在 Get 里的内容拿回手里”的用户。
- 信任感主要来自三点：本地优先、结构简单、可自托管和可查看源码。

### 文案方向

- 面向用户的页面只对访问者说话，不写协作过程。
- UI 里不要出现修改过程、设计原因、对话痕迹。
- 首页首屏只回答三件事：
  - 这是什么
  - 为什么有用
  - 现在该点哪里
- 更细的说明放到首屏下面。

### 页面方向

- 首页要轻、稳、容易扫读。
- 工具页重点是工作流，不要被次要链接抢走注意力。
- 隐私和 FAQ 可以放在首页里，但不能把 hero 挤满。
- 后续要尽量用真实截图替换纯文字说明块。

## 现在已经完成到哪里

结合现有文档，可以认为下面这些已经是项目现状的一部分：

- 已拆分落地页和工具页
- 已支持浏览器本地保存凭证
- 已有 `API Key` / `Client ID` 分步设置流程
- 已有笔记同步流程
- 已支持知识库、标签、关键词筛选
- 已支持正文、AI 总结、图片预览
- 已支持单篇 Markdown 导出
- 已支持多篇打包 zip 导出
- 已补充隐私、帮助、站点基础元信息等配套页面

## 还在持续收束的话题

这些更像“当前仍在推进中的讨论”，还不是完全结束的部分：

- 继续降低首页 hero 的信息密度
- 继续压缩首页下半部分文案长度
- 用截图型内容替换更多纯文本说明区块
- 继续检查移动端间距、导航和滚动节奏
- 继续收紧隐私说明和 FAQ 的篇幅
- UI 有阶段性变化后，及时同步项目文档

## 现有文档怎么分工

为了以后不再把项目上下文散得到处都是，建议这样使用文档：

- `README.md`
  - 面向外部的项目介绍
  - 快速开始
  - 基础说明
- `docs/PRD.md`
  - 产品范围
  - 功能边界
  - 路线方向
- `docs/PROGRESS.md`
  - 已完成内容
  - 阶段性进展
- `docs/UI-NOTES.md`
  - 首页和产品页的设计/文案原则
- `docs/TODO.md`
  - 短期待办
  - 可执行事项
- `docs/private/TECHNICAL_NOTES.md`
  - 内部技术记录
  - 实现细节、调试结论、技术风险
- `docs/PROJECT-CONTEXT.md`
  - 项目回看时的总入口
  - “我们已经定了什么”的整理页

## 后面怎么继续整理

以后有新的项目讨论，尽量当场归档，不要继续堆在聊天里：

- 产品范围或路线决定，写进 `docs/PRD.md`
- 已上线或已完成的阶段成果，写进 `docs/PROGRESS.md`
- 页面方向、文案边界、首页原则，写进 `docs/UI-NOTES.md`
- 明确的下一步任务，写进 `docs/TODO.md`
- 只给维护者看的技术细节，写进 `docs/private/TECHNICAL_NOTES.md`

如果一条新结论暂时不知道该归到哪里，先记在这份文档里，等它稳定以后再挪到更对应的位置。
